dbt biến SQL thành một quy trình có kiểm tra

Giả sử dữ liệu thô đã ở warehouse. Bạn muốn đổi tên cột, chuẩn hóa rồi tổng hợp thành bảng báo cáo. dbt tổ chức các SELECT thành model, biết model nào phụ thuộc model nào và chạy test để kiểm chứng. Hãy học SQL trước để đọc được SQL mà dbt sinh ra.

Từ vựng trước khi đọc tiếp

Model
Một phép biến đổi được viết bằng SELECT.
ref
Tham chiếu model khác đồng thời khai báo dependency.
Materialization
Cách lưu/kết xuất model: view, table, incremental...
Generic test
Rule dùng lại như unique hoặc not_null.

Đọc ví dụ theo từng bước

  1. Tạo stg_orders để chuẩn hóa dữ liệu nguồn.
  2. Model fct_sales dùng ref('stg_orders') để tính ở grain đã định.
  3. Test order_line_id không null và không lặp, rồi đối soát total với nguồn.
-- Model fct_sales; cú pháp {{ ... }} là Jinja của dbt.
SELECT order_line_id, quantity * unit_price AS amount
FROM {{ ref('stg_orders') }}

Kết quả và cách hiểu: dbt resolve tên bảng/view của stg_orders theo môi trường, dựng dependency và tạo SQL thực thi. Jinja chạy lúc biên dịch template; không chạy một macro Python cho từng row dữ liệu.

Dễ nhầm: Model chạy xong không chứng minh dữ liệu đúng. unique và not_null bảo vệ key; phải có thêm test business measure và freshness theo nhu cầu.

Tự kiểm tra: Vì sao không hard-code tên production.stg_orders trong mọi model?

ref biểu diễn dependency và giúp resolve theo môi trường. Test ở schema dev sẽ dễ kiểm soát hơn, đồng thời lineage cho biết downstream nào chịu ảnh hưởng.

Ôn các tình huống áp dụng trong bài ↓ · Xem câu hỏi và lời giải của unit

1. dbt giải quyết gì?

dbt quản lý phần Transform trong ELT: viết transformation bằng SQL/model, dựng dependency graph, chạy test, sinh documentation và đưa logic dữ liệu vào Git để review.

dbt không phải công cụ ingest và không tự lưu dữ liệu. SQL được compile rồi chạy trên warehouse/lakehouse đích.

2. Các khái niệm chính

  • Source: bảng do hệ thống khác nạp vào.
  • Model: một file SELECT; dbt materialize thành view/table/incremental/ephemeral.
  • ref(): tham chiếu model khác và tạo dependency.
  • source(): tham chiếu source đã khai báo.
  • Seed: file CSV nhỏ được quản lý trong project.
  • Snapshot: lưu lịch sử thay đổi, thường phục vụ SCD Type 2.
  • Test: assertion về chất lượng dữ liệu.
  • Macro: đoạn Jinja/SQL tái sử dụng.
-- models/marts/fct_orders.sql
select
    order_id,
    customer_id,
    order_date,
    amount
from {{ ref('stg_orders') }}
where status = 'completed'

Không hard-code database.schema.table khi có thể dùng ref/source.

3. Cấu trúc project gợi ý

models/
  staging/       -- rename, cast, chuẩn hóa gần nguồn
  intermediate/  -- logic trung gian, join/reuse
  marts/         -- fact, dimension, KPI cho business
seeds/
snapshots/
tests/
macros/
dbt_project.yml

Credentials thường nằm ngoài repository (ví dụ profiles.yml) hoặc ở secret manager của môi trường chạy.

4. Materialization

LoạiDùng khiTrade-off
viewNhẹ, luôn cần dữ liệu mớiQuery downstream có thể chậm
tableQuery nhiều, cần tốc độRebuild tốn thời gian/chi phí
incrementalBảng lớn, chỉ xử lý phần thay đổiLogic phức tạp hơn, phải xử lý late data
ephemeralLogic nhỏ chỉ để tái sử dụngCompile thành CTE, khó debug nếu lạm dụng

Incremental model cần unique key, filter dữ liệu mới và chiến lược cho record đến muộn. Phải test cả full refresh lẫn incremental/rerun.

{{ config(materialized='incremental', unique_key='order_id') }}

select * from {{ source('raw', 'orders') }}
{% if is_incremental() %}
where updated_at >= (select dateadd(hour, -2, max(updated_at)) from {{ this }})
{% endif %}

Lookback hai giờ chỉ là ví dụ; cửa sổ phải dựa trên SLA và đặc điểm nguồn.

5. Data tests

Trong YAML, khai báo description và test quan trọng:

models:
  - name: fct_orders
    description: One row per order.
    columns:
      - name: order_id
        data_tests: [not_null, unique]
      - name: customer_id
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_customers')
                field: customer_id

Ngoài unique/not_null/accepted_values/relationships, viết singular test cho rule nghiệp vụ: net amount không âm, completed order phải có payment...

6. Lệnh làm việc cốt lõi

dbt debug              kiểm tra connection/config
dbt compile            compile Jinja thành SQL
dbt run                chạy model
dbt test               chạy test
dbt build              build + test theo DAG
dbt docs generate      tạo metadata tài liệu
dbt docs serve         xem docs cục bộ

Dùng selection (model+, +model, tag/path/state) để chạy đúng model và dependency cần thiết.

7. Workflow Git và môi trường

  1. Developer sửa model ở schema dev riêng.
  2. Chạy format/lint, unit/data tests và dbt build phần bị ảnh hưởng.
  3. Pull request review cả SQL, grain, test và tác động downstream.
  4. CI dùng target tạm/isolated.
  5. Merge rồi deploy job production; artifact và run result được lưu để audit.

Không dùng production credential ở máy cá nhân. Không cho CI ghi vào schema production trong bước kiểm tra pull request.

8. Xử lý lỗi

  • Row count giảm: kiểm tra source freshness, filter, watermark và join loss.
  • Test relationship fail: tìm orphan key hoặc load order sai.
  • KPI đổi bất ngờ: so sánh lineage và commit gần nhất, đối soát từng layer.
  • Incremental tạo trùng: kiểm tra unique key, merge strategy, late updates.
  • Cost tăng: xem model rebuild toàn bộ, materialization và số lần chạy.

9. Bài thực hành

Tạo flow source orders -> stg_orders -> int_order_items -> fct_sales:

  • Khai báo source và freshness.
  • Dùng ref() cho dependency.
  • Thêm descriptions và 4 test cơ bản.
  • Cho fct_sales chạy incremental.
  • Chứng minh chạy lần hai không tạo trùng.
  • Sinh docs và xem lineage graph.

10. Checklist tự kiểm tra

  • Mỗi model có grain và description.
  • Dùng ref/source, không hard-code quan hệ.
  • Có test key, relationship và rule nghiệp vụ.
  • Incremental xử lý update/late data/rerun.
  • Secret không nằm trong Git.

Tài liệu chính: dbt Developer Hub.

11. source() và source freshness

Khai báo source biến raw table thành dependency có metadata:

sources:
  - name: raw_ecommerce
    database: ECOM_DWH
    schema: RAW
    loaded_at_field: ingestion_ts
    freshness:
      warn_after: {count: 2, period: hour}
      error_after: {count: 6, period: hour}
    tables:
      - name: orders

Freshness test hỏi dữ liệu cuối cùng đến lúc nào, khác với not_null/unique hỏi nội dung có hợp lệ không.

12. Staging model convention

Staging nên mỏng và gần source: rename, cast, standardize null/status, không nhồi business aggregation.

with source as (
    select * from {{ source('raw_ecommerce', 'orders') }}
), renamed as (
    select
        id::number as order_id,
        user_id::number as customer_id,
        lower(trim(status)) as order_status,
        created_at::timestamp as created_at,
        updated_at::timestamp as updated_at
    from source
)
select * from renamed

Một source table thường có một staging model chuẩn để downstream không lặp cast/rename.

13. Incremental: các câu hỏi bắt buộc

Trước khi chọn incremental, trả lời:

  • Cột nào thể hiện thay đổi? Có đáng tin và có timezone không?
  • Unique key là gì? Có duplicate từ source không?
  • Delete được truyền thế nào?
  • Late update tối đa bao lâu?
  • Khi logic code đổi, có cần full refresh/backfill không?

Lookback giảm bỏ sót nhưng tăng scan. MERGE cần deduplicate source trước nếu một key có nhiều update trong batch.

14. Snapshot và SCD2

Snapshot ghi lịch sử record mutable. Strategy timestamp dùng updated_at; check strategy so sánh cột. Timestamp thường scale/maintain tốt hơn nếu nguồn có cột tin cậy.

Snapshot không tự giải quyết mọi dimension: vẫn cần rename/map, surrogate key, unknown member và test khoảng hiệu lực trong mart.

15. Test theo tầng

  • Staging: accepted values, type/required key, source freshness.
  • Intermediate: relationship/cardinality, duplicate sau join.
  • Mart: unique grain, not null surrogate keys, business equation.
  • Reconciliation: tổng Gold so Silver/source theo cùng scope.
-- tests/assert_net_amount.sql: trả row sai; zero row = pass
select *
from {{ ref('fct_sales') }}
where abs(net_amount - (gross_amount - discount_amount)) > 0.01

16. Jinja và macro: dùng vừa đủ

Jinja tạo SQL lúc compile, không chạy theo từng row. Macro tốt cho pattern lặp có semantics ổn định; lạm dụng abstraction khiến compiled SQL khó đọc. Luôn xem output trong target/compiled khi debug.

17. CI selection và state

Trong PR, mục tiêu là build model thay đổi và downstream bị ảnh hưởng trong schema cô lập. State/defer có thể giúp tham chiếu production artifact cho model không đổi, nhưng CI identity không được ghi vào production.

Artifact quan trọng: manifest.json, run_results.json, catalog; dùng cho lineage, run audit và so sánh state.

18. Câu hỏi có đáp án

  1. dbt có move data từ API vào warehouse không? Không; dbt tập trung transform dữ liệu đã có trong platform.
  2. dbt run khác dbt build? Build chạy resources/test theo DAG; run chủ yếu chạy models.
  3. Test fail có tự rollback model đã build trước đó không? Không mặc định toàn DAG; thiết kế promotion/quality gate phù hợp.
  4. Incremental luôn rẻ hơn table? Không; merge scan lớn hoặc logic phức tạp có thể đắt, cần đo.

Vận dụng: hiểu lý do trước khi chọn đáp án

Vai trò của dbt

What is dbt mainly used for?

Xem đáp án đúng và cách suy luận

Building SQL-based transformations on data already loaded into the target platform

dbt chạy các phép biến đổi SQL trên dữ liệu đã được nạp vào nền tảng đích. Nó tổ chức model, dependency, test và tài liệu. Ví dụ raw_orders đã ở warehouse, dbt xây stg_orders rồi fct_sales để phục vụ phân tích.

ref tạo dependency

Why is a dbt model reference such as ref() useful?

Xem đáp án đúng và cách suy luận

It expresses model dependencies so dbt can build execution order and lineage

ref('stg_orders') khai báo model đang phụ thuộc stg_orders, giúp dbt sắp thứ tự build và ghi lineage. Nó còn resolve tên relation theo environment. Điều này tốt hơn hard-code tên bảng vì dependency trở nên kiểm tra được.

dbt trong workflow

Jinja và macro

What is the main purpose of Jinja or macros in a small dbt project?

Xem đáp án đúng và cách suy luận

Reduce repeated SQL patterns through reusable templating logic

Jinja sinh SQL từ template; macro đóng gói mẫu SQL lặp lại. Ví dụ chuẩn hóa cách tính net_amount ở nhiều model. Hãy kiểm tra compiled SQL vì đó mới là câu lệnh warehouse thực thi; tránh abstraction làm query khó hiểu.

unique kết hợp not_null

Which dbt generic tests are most appropriate for a column that is intended to be the model's primary key?

Xem đáp án đúng và cách suy luận

unique and not_null

unique kiểm tra không có hai dòng cùng khóa, not_null kiểm tra không thiếu khóa. Cột chỉ unique vẫn có thể có NULL theo cách test/engine xử lý, nên cần cả hai. Hai test này kiểm chứng identity của model nhưng chưa chứng minh các measure đúng.
