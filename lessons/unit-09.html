Azure: nơi chạy, nơi lưu và ai được truy cập

Cloud cung cấp tài nguyên qua dịch vụ thay vì bạn tự mua và quản lý tất cả máy chủ. Trong data platform, tách ba câu hỏi: dữ liệu ở đâu, compute nào xử lý và identity nào được phép làm việc. Các tên dịch vụ sẽ dễ nhớ hơn khi gắn với trách nhiệm.

Từ vựng trước khi đọc tiếp

Subscription
Cấp quản lý tài nguyên, quota và billing.
Resource group
Container logic cho tài nguyên liên quan để quản lý lifecycle và access.
Managed identity
Danh tính workload do Azure quản lý, dùng lấy token.
RBAC
Cấp role cho principal tại scope cụ thể.

Đọc ví dụ theo từng bước

  1. Một workload có resource group chứa storage và Data Factory.
  2. Pipeline dùng managed identity để xin token, rồi gọi storage.
  3. RBAC cho phép identity đọc raw và ghi curated; network cũng phải cho request đi tới đích.
Pipeline identity → token → Storage
                   quyền: read raw / write curated
                   mạng: DNS + route + firewall phù hợp

Kết quả và cách hiểu: Đúng identity chưa đủ nếu không có quyền; đúng quyền chưa đủ nếu DNS/firewall chặn. Phân tích theo từng lớp giúp xử lý lỗi 403 hoặc timeout có trật tự.

Dễ nhầm: Resource group không phải một bức tường network. Gom tài nguyên cùng group không tự cho chúng kết nối hoặc đọc dữ liệu của nhau.

Tự kiểm tra: Private endpoint có rồi nhưng hostname vẫn ra public IP: kiểm tra gì?

Name resolution và private DNS link trước. Ứng dụng cần resolve hostname dịch vụ tới private IP và có network path tới IP đó.

1. Mục tiêu

Hiểu cách Azure tổ chức tài nguyên, danh tính, mạng, chi phí và chọn building block cho một data platform cơ bản.

2. Cấu trúc quản lý tài nguyên

Microsoft Entra tenant
  -> Management Group (tùy quy mô)
    -> Subscription
      -> Resource Group
        -> Resource
  • Tenant: ranh giới danh tính của tổ chức.
  • Subscription: ranh giới billing/quota/quản trị.
  • Resource group: nhóm tài nguyên có vòng đời hoặc mục đích liên quan; một resource chỉ thuộc một resource group tại một thời điểm.
  • Region: khu vực địa lý triển khai dịch vụ.
  • Availability Zone: các nhóm datacenter tách biệt trong một region; hỗ trợ chịu lỗi tùy dịch vụ/region.

Không xem resource group như folder tùy ý. Nên nhóm theo môi trường và workload, ví dụ rg-ecom-data-dev-sea.

3. Shared responsibility

Azure bảo vệ datacenter, phần cứng và lớp cloud thuộc trách nhiệm của họ. Khách hàng vẫn chịu trách nhiệm về dữ liệu, identity, quyền truy cập, cấu hình mạng, secret và workload. Dịch vụ càng managed thì phần vận hành hạ tầng của khách hàng càng ít, nhưng trách nhiệm bảo vệ dữ liệu không biến mất.

4. Identity và authorization

  • Microsoft Entra ID: hệ thống identity.
  • Authentication: bạn là ai?
  • Authorization: bạn được phép làm gì?
  • Azure RBAC: gán role cho principal tại scope phù hợp.
  • Managed identity: danh tính cho Azure resource; ưu tiên hơn lưu account key/password trong code.

Nguyên tắc least privilege: cấp quyền tối thiểu, ở scope nhỏ nhất, trong thời gian cần thiết. Phân biệt control plane (quản lý resource) với data plane (đọc/ghi data).

5. Networking cơ bản

  • VNet/subnet: mạng riêng logic và phân đoạn tài nguyên.
  • NSG: rule allow/deny traffic ở network layer.
  • Private endpoint: đưa endpoint của dịch vụ PaaS vào VNet qua private IP.
  • Public network access/firewall: hạn chế nguồn được truy cập.
  • DNS: private endpoint chỉ hoạt động đúng khi name resolution đúng.

Khi pipeline timeout, ngoài code phải kiểm tra route, firewall, private endpoint, DNS và credential hết hạn.

6. Governance và resource hygiene

  • Naming convention nhất quán: workload, loại resource, env, region.
  • Tag tối thiểu: environment, owner, cost_center, data_classification.
  • Azure Policy để audit/deny cấu hình không chuẩn.
  • Resource lock cho tài nguyên quan trọng, nhưng phải có quy trình thay đổi rõ.
  • Infrastructure as Code để môi trường lặp lại được và review qua Git.

7. Cost mental model

Chi phí thường đến từ:

  • Compute chạy bao lâu và kích thước bao nhiêu.
  • Storage capacity, tier, transaction/list operation.
  • Data transfer/egress giữa region hoặc ra internet.
  • Số lần pipeline/activity chạy và integration runtime.
  • Log volume và thời gian retention.

Đặt budget/alert, tag để quy chi phí, auto-stop/auto-pause compute khi có thể. Không tối ưu bằng cách tắt monitoring cần thiết.

8. Data platform tối giản trên Azure

Sources
  -> Azure Data Factory (orchestrate/copy)
  -> Azure Data Lake Storage Gen2 (Bronze/Silver/Gold)
  -> Databricks/Spark hoặc SQL engine (transform)
  -> Warehouse/semantic model/Power BI (serve)

Cross-cutting: Entra ID, Key Vault, VNet/Private Endpoint,
Azure Monitor/Log Analytics, IaC, CI/CD

Tên sản phẩm không quan trọng bằng vai trò: ingest, store, process, serve, secure, observe.

9. Bài thực hành

Vẽ kiến trúc e-commerce dev:

  1. Một resource group và storage account.
  2. ADF copy batch từ source vào Bronze.
  3. Compute transform Bronze → Silver → Gold.
  4. Managed identity đọc/ghi đúng container.
  5. Private networking và log destination.
  6. Tag, budget và cách dọn resource thử nghiệm.

10. Checklist

  • Biết resource nằm ở tenant/subscription/resource group nào.
  • Không hard-code secret; ưu tiên managed identity.
  • Quyền được cấp theo least privilege.
  • Có tagging, budget và owner.
  • Kiến trúc có cả security, monitoring và recovery.

Tài liệu học tiếp: Azure fundamentals, Azure Architecture Center.

11. Region, zone và high availability

Chọn region theo data residency, service availability, latency và cost. Multi-zone giúp chịu lỗi datacenter trong region nếu dịch vụ hỗ trợ; multi-region xử lý region outage nhưng phức tạp và đắt hơn.

High availability không đồng nghĩa disaster recovery:

  • HA giảm downtime khi component lỗi.
  • Backup/versioning giúp khôi phục corruption/deletion.
  • DR quy định failover sang nơi khác theo RPO/RTO.

Mỗi dịch vụ trong pipeline có guarantee khác nhau; kiến trúc tổng thể chỉ mạnh bằng dependency yếu và runbook chưa test.

12. Identity flow mẫu

ADF managed identity
  -> RBAC/ACL đọc landing/incoming
  -> RBAC/ACL ghi bronze

Spark managed identity
  -> đọc bronze
  -> ghi silver/gold

BI identity
  -> chỉ đọc warehouse/gold đã publish

Không cấp cùng một identity quyền đọc raw PII, ghi Gold và quản trị resource. Tách identity theo workload/môi trường để giảm blast radius và audit rõ.

13. Network path để troubleshooting

Khi kết nối PaaS qua private endpoint:

  1. Tên host phải resolve về private IP.
  2. Route/NSG/firewall phải cho traffic cần thiết.
  3. Dịch vụ nguồn/sink phải cho subnet/private endpoint.
  4. Identity vẫn cần authorization data plane.

Timeout thường gợi ý network/path; 401/403 gợi ý identity/token/quyền; nhưng phải đọc error/log thay vì đoán.

14. Naming và tagging có mục đích

Ví dụ stde01prodsea01 có thể theo constraint storage account; tên khác như rg-de01-prod-sea. Naming convention cần bảng viết tắt, environment, region, workload và uniqueness rule.

Tag phục vụ owner/cost/automation nhưng không phải security boundary. Policy có thể yêu cầu tag hoặc deny public network, sai region, thiếu diagnostic settings.

15. Infrastructure as Code lifecycle

code change -> validate/lint -> plan/what-if -> review
-> deploy non-prod -> verify -> approval -> prod

Không sửa portal thủ công rồi quên cập nhật IaC vì tạo configuration drift. Secret không nằm trong state/output công khai; state backend phải được bảo vệ và lock.

16. Worked architecture decision

Yêu cầu: e-commerce daily analytics, nguồn SQL on-prem, dữ liệu nhạy cảm, team nhỏ.

  • ADF + self-hosted IR để đi vào on-prem network.
  • ADLS Gen2 làm Bronze/Silver/Gold.
  • Spark/Databricks cho transform lớn; dbt/SQL cho mart.
  • Managed identity + Key Vault, private endpoints theo threat model.
  • Azure Monitor/Log Analytics cho telemetry.
  • Một region ban đầu, backup/versioning và DR plan theo RPO/RTO.

Ghi decision record: context, options, decision, trade-off và điều kiện xem xét lại.

17. Câu hỏi có đáp án

  1. Resource group có phải security boundary tuyệt đối? Không; nó là management scope, quyền vẫn do RBAC/resource policy/data plane.
  2. Managed identity có nghĩa không cần phân quyền? Không; identity vẫn cần role tối thiểu.
  3. Private endpoint có tự sửa DNS không? Cần cấu hình/resolution đúng, nhất là hybrid network.
  4. Tag có chặn user đọc dữ liệu không? Không; dùng RBAC/ACL/policy phù hợp.

Vận dụng: hiểu lý do trước khi chọn đáp án

Đọc tình huống, tự giải thích bằng lời của bạn rồi đối chiếu lời giải. Câu hỏi tiếng Anh giữ các thuật ngữ chuyên môn; phần giải thích dùng tiếng Việt.

Resource group

In Azure, what is a resource group?

Xem đáp án đúng và cách suy luận

A logical container used to organize related resources for lifecycle and access management

Resource group là container logic gom tài nguyên Azure để quản lý lifecycle và quyền theo scope. Ví dụ một storage và Data Factory thuộc cùng workload. Subscription vẫn là cấp quản lý riêng; resource group không phải firewall hay database schema.
